# Integration plan — keep the existing engine intact

1. **Agree the adapter contract.** Map audit-run ID, ledger metadata, currency, finding ID, rule/version, vendor ID, record IDs, integer minor-unit amount, evidence facts and readiness. Keep rule output separate from human decisions. Normalize the current engine's findings into this model at the boundary; do not scatter translations across screens.
2. **Validate money semantics first.** Separate candidate amount, unverified exposure, future savings, claimed amount and recovered amount. De-duplicate overlapping findings against one payment before aggregating. Preserve currency boundaries. Add partial claims/recoveries, write-offs and reversals as explicit events before production. Prototype full-amount transitions are deliberately limited.
3. **Replace fixtures through a repository interface.** Introduce loadRun, listFindings, getEvidence, listRecords, saveNote, createDraft and recordOutcome operations. Keep this prototype and the old dashboard independently runnable while the adapter is tested. Do not route production users to v2 by default.
4. **Connect authentic evidence.** Resolve file/page/row references to immutable originals. Distinguish extracted facts from inferred matches and missing information. Validate invoice totals, credits, contracts, service periods and payment references. Never treat this prototype's authored supporting facts as real audit evidence.
5. **Move state to authenticated storage.** Replace local storage with permission-checked, revisioned persistence. Enforce transition guards server-side, idempotency, concurrent-edit handling and immutable actor/timestamp/reason history. Add workspace isolation and sensitive-data redaction.
6. **Treat vendor contact as a separate integration.** Draft preparation must not imply sending. Add recipient verification, permission checks, attachment previews and explicit send confirmation. Verify received funds through accounting data rather than button clicks.
7. **Migrate UI incrementally.** Reuse the documented tokens and interaction contracts in the existing framework only after review. Start with a gated Findings route and evidence panel, then Recovery, Records and Overview. Preserve old routes and feature flags until reconciliation, accessibility, cross-browser and end-to-end tests pass.

Acceptance for real-data rollout: a frozen audit run produces matching totals in engine and UI; overlapping findings cannot inflate recovery; permissions hold; back/forward and deep links work; all mutations are auditable; failures preserve edits; reduced motion and keyboard use remain functional. Deployment and replacement of the current application require separate approval.
